1. ビルド成功の要因（Makefile 変更不要の理由）

Makefile に手動で -lsimple_math を追記しなかったにもかかわらずビルドが通った理由は、MicroPython のビルドシステムが、ユーザーCモジュールを処理する際に実行する以下のステップにあります。

  1. オブジェクトファイルの生成： make は triple.c をコンパイルし、build-coverage/simple_math/triple.o というオブジェクトファイルを生成します。

  2. 静的ライブラリの生成： MicroPython は、通常、ユーザーモジュールディレクトリごとに静的ライブラリ（この場合は libsimple_math.a に相当するファイル）を生成します。

  3. 自動的なリンカ引数： ports/unix の Makefile の内部で、USER_C_MODULES を指定した場合、ビルドシステムがそのモジュール群から生成された全ての静的ライブラリを、自動的にリンカへの入力ファイルとして追加するように設定されている可能性が高いです。

つまり、MP_REGISTER_MODULE マクロを定義した C ファイルがコンパイルされ、そのオブジェクトファイルが最終的な micropython 実行ファイルに静的にリンクされたため、実行ファイルには simple_math モジュールが最初から組み込まれた状態になったということです。

2. 再度の問題発生：ImportError の原因

しかし、最初の実行結果では、再度 ImportError: no module named 'simple_math' が発生しています。

  1. 静的リンクエラー： モジュールは実行ファイルに含まれているが、MicroPython の初期化処理（mp_init）で、登録マクロ (MP_REGISTER_MODULE) を有効にするための処理が漏れている。

はい、その通りです。ご提示したコードは、MicroPython（およびそのフォークであるCircuitPython）のランタイムシステムと連携するために設計された専用のAPIとマクロを使用しています。

標準的なC言語の知識だけでは読み解けない、MicroPython特有の主要な概念は以下の4点です。

1. すべてが mp_obj_t （万能オブジェクト型）

Pythonは動的型付け言語であるため、C言語側ではすべての変数を抽象化された型で扱う必要があります。

  • mp_obj_t: MicroPythonにおける「Pythonオブジェクト」を表す汎用ポインタ型です。整数、浮動小数点数、リスト、文字列など、すべてのデータはこの型として受け渡しされます。

  • タグ付きポインタ (Tagged Pointer): メモリ効率を極限まで高めるため、MicroPythonは多くの場合、ポインタの下位ビットを使って「小さな整数」などをヒープ割り当てなしで直接埋め込んでいます（31bit整数など）。mp_obj_t は単なるメモリアドレスではなく、データそのものである可能性があります。

2. 型変換マクロ (mp_obj_get_int / mp_obj_new_int)

C言語のプリミティブ型（int, float）と、Pythonのオブジェクト（mp_obj_t）を相互変換するために必須の関数群です。

  • mp_obj_get_int(arg): mp_obj_t が整数型であることを確認し（異なれば TypeError を送出）、C言語の mp_int_t（通常は long 相当）を取り出します。タグ付きポインタのデコードもここで行われます。

  • mp_obj_new_int(result): C言語の整数をPythonオブジェクトにエンコードします。値が小さければタグ付きポインタになり、大きければヒープメモリを確保して mp_obj_int_t 構造体を作成します。

3. 静的な登録システム (ROM化)

PC向けのCPython拡張モジュール（.pyd/.so）は実行時に動的にメモリを確保してモジュール定義を行いますが、MicroPythonはRAMを節約するため、コンパイル時に定数データ（ROM）として構造体を作成します。

  • MP_DEFINE_CONST_FUN_OBJ_1: 関数オブジェクトを定数 (const) として定義します。_1 は引数が1つであることを示し、呼び出し時の引数チェックを自動化します。

  • mp_rom_map_elem_t: 辞書（モジュールのグローバル名前空間）の要素をROM上に配置するための型です。これにより、モジュールをインポートしてもRAMを消費しません。

4. QSTR (Quick String)

コード中の MP_QSTR_simple_math や MP_QSTR_triple は、インターニングされた文字列（Interned String） のIDです。

  • MicroPythonは、ソースコード中のすべての識別子（関数名、変数名など）を収集し、ビルド時に一意なID（QSTR）を割り当てます。

  • 実行時の文字列比較を「ポインタ比較」や「整数比較」だけで行えるため、非常に高速かつ省メモリです。ビルド時に QSTR updated というログが出ていたのは、このIDテーブルを生成していたためです。

Ports/unixのMicroPythonは、サブプロセスを呼び出すとかの追加機能も含まれていますか?

結論

標準ライブラリとしては含まれていませんが、FFI (Foreign Function Interface) を経由することで実現可能です。

CircuitPython の Unix ポートは、本家 MicroPython の Unix ポートと比較して API が厳格に制限されており、セキュリティと移植性の観点から os.system や subprocess モジュールは標準では無効化（または削除）されています。

しかし、先ほどのビルドプロセスで libffi をリンクした通り、ffi モジュール は有効になっています。これを利用してホスト OS (Linux) の標準 C ライブラリ (libc) 内にある system 関数を直接呼び出すことで、任意のサブプロセス実行が可能になります。
